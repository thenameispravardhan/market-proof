Project name:    AI News Trading Bot
Version:         1.0.0 (app/__init__.py)

Platform:        Windows (PowerShell). Also has bash scripts for *nix-style runs.
Genre:           Local-first, AI-driven intraday equity news-trading system for

Audience:        Single local operator (you). No multi-tenant auth, no public

--------------------------------------------------------------------------------
1. WHAT IT DOES (in one sentence)
--------------------------------------------------------------------------------
It watches corporate-announcement feeds on NSE/BSE the moment they are filed,
asks a large language model (DeepSeek) to read the actual filing text and
classify the event, runs the result through an operator-authored rules engine
and a risk engine, and (in paper or live mode) places an entry/exit trade on
Fyers — all inside a tight 20-second budget from `filed_at` to order on the
wire.

--------------------------------------------------------------------------------
2. WHY IT EXISTS (the problem it solves)
--------------------------------------------------------------------------------
Material corporate announcements (order wins, M&A, resignations, buybacks,
results) move NSE/BSE stocks in seconds. By the time a human sees a Telegram
forward, the move is half over. The bot's job is to be first reader and
first trader, with explicit risk gates so it cannot bleed the account.

--------------------------------------------------------------------------------
3. ARCHITECTURE — HIGH-LEVEL PIPELINE
--------------------------------------------------------------------------------
The system is split into six tracks (T1..T6). They are wired together through
a single in-process event bus (app/services/event_bus.py), with each stage
owning its own SQLite-backed state and its own asyncio lifecycle:

    NSE/BSE filings  ─►  T2 Monitor  ─►  T3 Analyzer  ─►  T4 Execution
                                                              │
                                                              ▼
                          ◄──  T5 Notifications / Webhooks  ◄──┘
                                T1 infrastructure: FastAPI + WS + DB

T1 — Infrastructure (app/main.py, app/api/*, app/db/*, app/services/*)
    FastAPI app, lifespan-managed startup/shutdown, SQLite via SQLAlchemy,
    WebSocket event bus, global Settings (app/config.py), correlation IDs,
    structlog JSON logging, /ws endpoint, static SPA hosting.

T2 — Monitors (app/monitors/{nse,bse,base,manager}.py)
    Polls NSE & BSE corporate-announcement endpoints every POLL_INTERVAL_SECONDS
    (default 2s, httpx fast path + Playwright fallback), normalizes results,
    dedupes against the `announcements` table, publishes `announcements.new`
    on the event bus. PDF prefetch + lang-detection + scoring happens here too.

T3 — Analyzer (app/analyzer/*)
    Subscribes to `announcements.new`. Has TWO tracks:
      • Deterministic fast track (fast_track.py) — order wins with explicit
        Rs-crore value, KMP resignations, buybacks — goes straight to the
        rules engine, llm_ms=0.
      • LLM track (deepseek_client.py) — sends prompt + filing text to
        DeepSeek, validates JSON via pydantic (schemas.py), then the same
        rules engine evaluates signal_rules rows. Persists `analyses` and
        emits `signals.new`.

T4 — Execution (app/execution/*)
    ExecutionManager routes every signal through risk checks → position sizing
    → paper or live order → reconciliation → trade manager (SL/target/time
    exits, scale-out, trailing). Supports two backends:
      • paper.py  — synthetic fills with realistic slippage + latency.
      • fyers_live.py / fyers_stream.py — REST + the fyers-apiv3 WebSocket
        for live data + order fill updates.

T5 — Notifications & Webhooks (app/notifications/*, app/webhooks/*)
    NotificationManager fans events out to operator-curated channels:
    Telegram, Discord, Email, generic Webhook. WebhookDispatcher handles
    outbound HTTP for both Fyers postback-style hooks and arbitrary
    user-configured endpoints.

T6 — Operational surfaces (app/api/*)
    Health, audit log, settings, prompts, rules, strategies, broker accounts,
    backtests, market data, orders, positions, risk — all exposed as a JSON
    REST API under /api/* and consumed by the React dashboard.

6. KEY CONCEPTS
--------------------------------------------------------------------------------
TRADING_MODE (app.config.Settings.TRADING_MODE)
    "paper" — synthetic fills via paper.py. Default.
    "live"  — real orders via fyers_live.py + fyers_stream.py. Requires
              a connected Fyers account AND the operator-created
              sentinel file .i_accept_live_risk (gitignored).

The 20-second budget
    Filing hits NSE/BSE → monitor scrapes → analyzer reads + reasons → risk
    approves → order hits Fyers. The whole chain must finish before the
    news alpha decays. Hard controls:
      MAX_NEWS_AGE_SECONDS = 90  (analyzer refuses anything older)
      LLM_TIMEOUT_SECONDS  = 18  (LLM call deadline)
      PIPELINE_DEADLINE_SECONDS = 0 by default; opt-in from Settings
      MAX_HOLD_SECONDS = 1080   (force-square after 18 min)

Two-track analyzer
    Fast track (deterministic, ~ms): "wins order worth Rs X cr", KMP
    resignation (MD/CEO/CFO/WTD/chairman), buyback with value. Goes
    straight to the rules engine with llm_ms=0.
    LLM track (slow, paid): everything else. DeepSeek reads the actual
    filing text and returns a structured AnalysisResponse.
    Both tracks feed the SAME rules engine and the SAME risk layer.

Operator-curated rules (not hard-coded logic)
    The bot has zero hard-coded "if order-win then BUY". The rules engine
    evaluates `signal_rules` rows in the database. You author them in the
    Rules UI — match patterns, sentiment thresholds, key-number filters,
    event-type gates — and the engine combines them with AND/OR/NOT
    groups. This is what makes the bot a "platform" rather than a strategy.

Prompt templates are data
    DeepSeek system prompts live in the `prompt_templates` table and are
    editable from the Prompts page (versioned, with history and reset-to-
    default). Restart never overwrites them. The DEFAULT template seeds
    on first boot only.

Risk framework (RISK.md is referenced throughout)
    §1 Pre-trade filters: sentiment confidence floor, India VIX cap,
       spread cap (L1 feed pending — NO-OPs), ADV floor.
    §2 Position sizing: risk-based qty AND notional cap, smaller wins.
       Fresh accounts ramp RISK_RAMP_START_PCT → MAX_CAPITAL_RISK_PCT
       over RISK_RAMP_TRADES filled trades. INTRADAY_LEVERAGE=5x
       applies to notional sizing only, never to real-money risk.
    §3 Stops / targets: SCALE_OUT at SCALE_OUT_R, trailing armed at
       TRAIL_ACTIVATE_R, ATR-aware initial stop (ATR×ATR_STOP_MULT
       clamped to [DEFAULT_SL_MIN_PCT, ATR_MAX_STOP_PCT]).
    §4 Portfolio circuit breakers: daily / weekly / monthly loss caps
       (% of anchor equity). Daily+monthly flatten + halt; weekly
       throttles risk-per-trade. Consecutive-loser pause.
    §4b Clustering: SECTOR_CONCENTRATION_PCT (whole-portfolio sector
       cap), MAX_POSITIONS_PER_SECTOR, SECTOR_CLUSTER_WINDOW_SECONDS
       (block a 2nd same-sector entry inside the window).
    §5 Execution safeguards: IOC marketable-limit at last±ENTRY_BUFFER_PCT
       cancelled after ORDER_FILL_TIMEOUT, fill worse than MAX_SLIPPAGE_PCT
       rejected.

Outcome logger (Phase 4)
    Every approved AND blocked signal writes a `signal_outcomes` row with
    the Fyers price at signal time and +5m/+30m. Pure telemetry — no
    trading influence — but it's the win-rate report and the future ML
    dataset. Defaults ON.

10. THE ROADMAP (plan.txt)
--------------------------------------------------------------------------------
The improvement plan in plan.txt is the project's north star. Constraint:
NEVER destroy the existing setup — every new behavior ships behind a
frontend toggle, defaulting to the current behavior. No file sentinels,
no CLI gates. Controls live in the UI.

Phase 0 — Measure first: instrument per-stage latency (pdf_fetch_ms /
    pdf_extract_ms / llm_ms / total_ms / news_age_s_at_start), log an
    analyzer.pipeline_timing line, then read the logs. STATUS: DONE for
    instrumentation, PENDING for the operator to read them.

Phase 1 — Real news text into the pipeline: PDF prefetch + extraction +
    Hindi filter + page selection + scanned-PDF detection +
    {{extracted_text}} placeholder + "Send extracted PDF text to AI"
    toggle (default OFF). STATUS: DONE.

Phase 2 — Two-track signals: deterministic fast track (order wins,
    KMP resignations, buybacks) routed straight to the rules engine.
    XBRL parser for financial results is DEFERRED until live XBRL
    attachments are mapped. STATUS: DONE.

Phase 3 — LLM track under ~8s: LLM_MAX_TOKENS 1024→400, end-to-end
    deadline, retries trimmed, MAX_NEWS_AGE_SECONDS exposed. Live
    benchmark 2026-07-04: PDF fetch 200-1200ms, extract <80ms,
    DeepSeek deepseek-v4-flash ~2.3-2.4s, TOTAL ~2.5-2.7s off-peak.
    STATUS: DONE off-peak; verify market-hours p95.

Phase 4 — Data collection: outcome logger writes to signal_outcomes;
    review/export view for label correction. STATUS: DONE (logger
    running, review view is ongoing).

Phase 5 — Pre-filter model: weak-label by "+X% vs index within 30 min",
    train FinBERT/IndicBERT-class classifier (<100ms) to kill routine
    noise before the LLM call. STATUS: BLOCKED on Phase 4 data volume
    (needs 1-2k logged announcements).

Phase 6 — Fine-tuning: only after 1-2 months of Phase 4 data, on fact
    extraction (not buy/sell direction — the rules engine stays the
    decision-maker). STATUS: BLOCKED.

Dependency graph:
    Phase 0 runs alongside Phase 1 → Phase 1 unlocks everything →
    Phases 2 and 3 are independent of each other → Phase 4 needs
    Phase 1 → Phase 5 needs Phase 4 → Phase 6 needs months of Phase 4.

       on localhost for dev; scripts/start_webhook_tunnel.ps1 handles this)

Going live
    Edit .env: TRADING_MODE=live, set FYERS_ACCESS_TOKEN, add live
    account under Accounts in the UI, then create the operator sentinel
    file `.i_accept_live_risk` (gitignored). The file MUST exist; the
    app refuses to enter live mode without it.

12. DESIGN PHILOSOPHY / RULES OF THE ROAD
--------------------------------------------------------------------------------
• Operator-curated, not hard-coded. The bot ships with no "BUY on order
  win" rule. You write the rules in the Rules UI; the engine evaluates
  them. Same for prompts — templates live in the DB.
• All knobs in the UI. No file sentinels, no CLI flags. The Settings
  page owns every dial; restart must never silently change behavior.
• Restart-safe. Prompts overwrite=False on seed; rules never re-seed;
  saved overrides re-apply at boot. Deleting a rule stays deleted.
• Fail-safe defaults. Features that need a feed they don't yet have
  (VIX, L1 spread, ADV) NO-OP rather than fake a pass.
• Latency is the product. Every layer measures itself. Logs carry
  per-stage ms; the operator reads them.
• Speed is a feature, but not at any cost. Risk gates, sector cluster
  windows, freshness caps, and circuit breakers ALWAYS run before
  the order goes out.
