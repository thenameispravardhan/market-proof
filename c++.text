1.6 WHAT THIS MEANS FOR THE REWRITE

    The pre-signal path (detection → analysis) is 99.997% network wait. No
    amount of C++ changes it. The rewrite CANNOT be justified on end-to-end
    signal latency and must not be defended on that basis.

    The place where microseconds genuinely matter in this system is the
    POST-signal path: tick-by-tick stop-loss and target evaluation in
    trade_manager, and order dispatch once a decision is made. Every tick is
    a chance to exit late and eat slippage. That path is currently Python
    asyncio on a shared event loop with the monitors, the LLM client and the
    REST API. THAT is the defensible performance target of this migration:

        TARGET: tick-to-exit-order-dispatch, p99 < 50 us
                (currently unmeasured; instrument before you optimise)

    Secondary defensible targets:
        - Memory: 1.36 GB → < 150 MB (removes the live OOM risk)
        - Startup: 25–40 s → < 1 s (restart during market hours becomes safe)
        - Deterministic latency: no GC pauses, no GIL contention

2.3 THE 2-vCPU PROBLEM — READ THIS BEFORE DESIGNING THREADS

    The classic HFT architecture is: one thread spins on the feed, one thread
    runs strategy, one thread dispatches orders, each pinned to an isolated
    core, all communicating over lock-free ring buffers, never sleeping.

    You have ONE physical core. A spinning thread consumes 50% of your total
    compute and starves the OS, SQLite, Caddy and the LLM HTTP client. On
    this box, busy-wait is not an optimisation — it is a denial-of-service
    against your own system.

    DESIGN RULE FOR THIS MIGRATION:
      - Use lock-free ring buffers (they are correct and cheap), but use a
        HYBRID wait strategy: bounded spin (~1–2 us with _mm_pause()) then
        fall back to a futex/condition-variable sleep.
      - Never pin a permanently-spinning thread.
      - Budget threads: 1 hot thread (feed + tick/exit evaluation), 1 worker
        pool (HTTP, LLM, PDF, DB writes), 1 Drogon event loop. Oversubscribed
        by design; the hot thread gets priority via SCHED_FIFO with a low
        rt_runtime cap.
      - Revisit ONLY if you move to the hardware in Appendix D.

2.4 CONSEQUENCE

    On current infrastructure the achievable win is:
      - deterministic microsecond-scale tick→exit path  (real)
      - ~10x memory reduction                            (real)
      - ~30x faster startup                              (real)
      - kernel-bypass-class nanosecond wins              (NOT achievable)

    If you want the full HFT stack, Appendix D lists what to move to. Decide
    that BEFORE Phase 9, because it changes the threading model.

SECTION 3 — INVARIANTS THAT MUST SURVIVE
================================================================================
These come from PROJECT.txt §25 and are load-bearing safety properties, not
preferences. The C++ system is WRONG if it violates any of them, no matter how
fast it is. Encode each as a test in the parity harness (Section 10).

  I1  Fyers-only pricing. All quotes/candles/VIX from Fyers. No public-feed
      fallback, ever.
  I2  No synthetic entry fill. A cold feed BLOCKS the entry with
      NO_LIVE_PRICE. It never fills at an invented price.
  I3  Intraday only, no carry-forward. MIS only. TIME_EXIT and EOD square-off
      always flatten.
  I4  Fyers "enabled" is a TRADE switch only. Turning it off blocks orders but
      keeps the feed and OAuth alive.
  I5  Rules are a fresh slate. No hard-coded triggers. Deleted rules never
      resurrect.
  I6  Explicit levels win over scale-out. An explicit target = full exit.
  I7  Frontend-only control. Every switch in the UI. No file sentinels, no CLI
      gates. "LIVE" requires a typed confirmation.
  I8  Non-destructive evolution. Every new behaviour behind a toggle that
      defaults to current behaviour.
  I9  Early entry is the edge. Never fix whipsaw by delaying entry; fix the
      stop, the sizing or the caps.
  I10 Extracted-text mode degrades to the legacy prompt; it never blocks a
      signal.

  ADDITIONAL INVARIANTS INTRODUCED BY THIS MIGRATION:
  I11 No undefined behaviour on the order path. UBSan+ASan clean, always.
  I12 No unbounded allocation during market hours (09:15–15:30 IST).
  I13 Every C++ decision must be reproducible from logged inputs (Section 10).

SECTION 4 — STRATEGY: STRANGLER-FIG, NOT BIG-BANG
================================================================================

4.1 WHY NOT BIG-BANG

    A big-bang rewrite of a live trading system means: months with no working
    product, no way to test against reality, and a single terrifying cutover
    where 52,000 lines of new C++ touch real money for the first time
    simultaneously. Historically this is how rewrites die.

4.2 THE APPROACH

    Strangler-fig. The C++ binary starts as a process that does nothing, runs
    ALONGSIDE the Python bot, and takes over one responsibility at a time. At
    every point in the migration there is a working, deployable trading
    system. You can stop at any phase boundary and still have a product.

    Three coexistence mechanisms, used in this order:

    (a) SHADOW  — C++ consumes the same inputs, produces decisions, writes
                  them to a separate table, places NO orders. Decisions are
                  diffed against Python. This is how every risky component
                  earns trust.

    (b) PROXY   — Python delegates a specific job to C++ over a Unix domain
                  socket, and falls back to its own implementation on any
                  error or timeout. Non-destructive per invariant I8.

    (c) OWNER   — C++ owns the responsibility outright; Python code deleted.

    Every phase moves one component through (a) → (b) → (c).

4.3 THE SHARED DATABASE IS THE SEAM

    Both stacks read and write the same SQLite file. SQLite in WAL mode
    supports multiple processes safely. This is what makes incremental
    migration possible without a distributed-systems problem.

    RULES:
      - One writer per table at any given time. Document ownership in a table
        in this file and update it as phases complete.
      - Use BEGIN IMMEDIATE for write transactions to avoid SQLITE_BUSY
        upgrade deadlocks.
      - busy_timeout = 30000 in both stacks.
      - Never hold a write transaction across a network call. (The Python
        code already violates this in places — fix during port, do not
        replicate.)

5.2 THREAD BUDGET (2 vCPUs — see 2.3)

    HOT      1 thread   SCHED_FIFO prio 50, rt_runtime capped at 60%
                        hybrid spin (2 us) then futex sleep
    WORKER   2 threads  SCHED_OTHER, blocking I/O allowed
    DROGON   1 thread   SCHED_OTHER, event loop for REST/WS

    Oversubscribed deliberately. Context-switch overhead is irrelevant next
    to a 34-second exchange lag; determinism on the HOT thread is what
    matters, and SCHED_FIFO provides it.

5.3 DATA FLOW — HOT PATH (the part that justifies the rewrite)

    Fyers data frame
      -> io_uring recv into a pre-allocated slab      [zero alloc]
      -> decode into Tick (POD, cache-line sized)
      -> publish to MarketDataBus (open-addressed, symbol_id keyed)
      -> scan managed positions for this symbol:
             stop / target / trail / time-exit         [branchless]
      -> on trigger: build Order from a pool           [zero alloc]
      -> push to order ring
      -> WORKER thread performs the HTTPS order POST

    Everything up to "push to order ring" is allocation-free, exception-free
    and lock-free. That is the microsecond budget.

5.4 DATA FLOW — COLD PATH (99.997% network wait — optimise for clarity)

    NSE/BSE/RSS poll -> parse -> dedupe -> SQLite insert -> event
      -> PDF prefetch -> extract -> prompt render -> DeepSeek HTTP
      -> JSON parse -> schema validate -> rules engine -> risk engine
      -> signal -> entry state machine -> order

    Write this code to be BORING AND OBVIOUS. Lock-free techniques here buy
    nothing measurable and cost correctness. Section 8 techniques apply to
    5.3, not to 5.4. Applying them here is the over-engineering this project
    exists to avoid.

5.5 CORE TYPE: Symbol
--------------------------------------------------------------------------------
Strings on the hot path are the most common self-inflicted performance wound.
Symbols become integers at the boundary and never become strings again until
they leave.

    // Generated at BUILD TIME from the instrument master.
    // ~2,000 NSE cash symbols -> dense uint16 ids.
    using SymbolId = std::uint16_t;
    inline constexpr SymbolId kInvalidSymbol = 0xFFFF;

    // frozen::unordered_map gives O(1) lookup with ZERO runtime
    // construction and no allocation. Built by a codegen step that reads
    // data/scrip_master/*.csv and emits symbols_generated.hpp.
    constexpr frozen::unordered_map<frozen::string, SymbolId, 2048>
        kSymbolTable = { {"RELIANCE", 0}, {"TCS", 1}, /* ... */ };

    // Reverse direction: a flat array, indexed directly. No hashing.
    inline constexpr std::array<std::string_view, 2048> kSymbolNames = {...};

    RULE: resolve the string ONCE, at ingest. Everything downstream —
    MarketDataBus, positions, orders, rings — carries SymbolId only.

5.6 CORE TYPE: Tick (cache-line resident)
--------------------------------------------------------------------------------
    struct alignas(64) Tick {
        std::uint64_t exch_feed_time_ns;   //  8
        std::int64_t  ltp_e2;              //  8  price in paise, INTEGER
        std::int64_t  bid_e2;              //  8
        std::int64_t  ask_e2;              //  8
        std::int64_t  volume;              //  8
        std::uint32_t seq;                 //  4
        SymbolId      symbol;              //  2
        std::uint16_t flags;               //  2
        std::uint64_t recv_tsc;            //  8  rdtsc at ingest, for latency
    };                                     // 56 bytes -> one cache line
    static_assert(sizeof(Tick) == 64);
    static_assert(std::is_trivially_copyable_v<Tick>);

WHY INTEGER PRICES (ltp_e2 in paise, not double):
  - Exact. No accumulated FP error in P&L across 27,000 trades.
  - Comparisons are integer compares: faster and exactly ordered.
  - The wire format already delivers scaled integers (see 7.4) — converting
    to double and back is both slower and lossy.
  - Convert to double ONLY at the API/JSON boundary.

  This is a genuine correctness improvement over the current Python floats,
  independent of speed. Money should not be a binary fraction.

--------------------------------------------------------------------------------
5.7 MarketDataBus — open-addressed, no allocation, no locks
--------------------------------------------------------------------------------
The Python version is a dict guarded by the event loop. The C++ version is a
flat array indexed by SymbolId. There is no hashing at all, because SymbolId
is already dense.

    class MarketDataBus {
        // Direct-indexed. 2048 * 64B = 128 KB — fits comfortably in L2.
        alignas(64) std::array<Tick, kMaxSymbols> slots_{};
        alignas(64) std::array<std::atomic<std::uint32_t>, kMaxSymbols> seq_{};
      public:
        // Seqlock write: odd during write, even when stable.
        void publish(const Tick& t) noexcept {
            auto& s = seq_[t.symbol];
            const auto v = s.load(std::memory_order_relaxed);
            s.store(v + 1, std::memory_order_release);   // -> odd
            slots_[t.symbol] = t;                        // 64B store
            s.store(v + 2, std::memory_order_release);   // -> even
        }
        // Wait-free read; retries only if a write raced.
        [[nodiscard]] bool read(SymbolId id, Tick& out) const noexcept {
            for (;;) {
                const auto a = seq_[id].load(std::memory_order_acquire);
                if (a & 1u) [[unlikely]] { continue; }
                out = slots_[id];
                const auto b = seq_[id].load(std::memory_order_acquire);
                if (a == b) [[likely]] { return true; }
            }
        }
    };

WHY A SEQLOCK: exactly one writer (the hot thread) and many readers (REST
API, dashboard). Readers never block the writer — the opposite of a mutex,
where a slow dashboard request could delay a stop-loss check. This is the
single most valuable structure in the design.

5.8 POSITION BOOK — Struct-of-Arrays for the per-tick scan
--------------------------------------------------------------------------------
This is the hottest loop in the system: on every tick, every open position on
that symbol must be checked for stop, target, trail and time exit.

    ARRAY-OF-STRUCTS (the naive port — do NOT do this):
        struct Position { SymbolId sym; int64_t stop, target, entry; ... };
        std::vector<Position> book;   // pointer chasing, 1 cache miss/position

    STRUCT-OF-ARRAYS (do this):
    class PositionBook {
        static constexpr std::size_t kMax = 64;   // MAX_OPEN_POSITIONS
        alignas(64) std::array<SymbolId,    kMax> sym_{};
        alignas(64) std::array<std::int64_t, kMax> stop_{};
        alignas(64) std::array<std::int64_t, kMax> target_{};
        alignas(64) std::array<std::int64_t, kMax> trail_high_{};
        alignas(64) std::array<std::uint64_t, kMax> deadline_ns_{};
        alignas(64) std::array<std::uint8_t,  kMax> side_{};   // 1=long 0=short
        std::size_t n_ = 0;
    };

    With 64 positions, sym_ is 128 bytes = 2 cache lines. The whole scan
    touches ~6 cache lines total instead of 64 pointer-chased objects.

    BRANCHLESS EVALUATION:
        // Returns a bitmask of triggered positions. No branches in the loop
        // body -> no mispredictions -> the loop runs at ~1 element/cycle.
        std::uint64_t scan(SymbolId s, std::int64_t ltp, std::uint64_t now) {
            std::uint64_t hit = 0;
            for (std::size_t i = 0; i < n_; ++i) {
                const bool match = (sym_[i] == s);
                const bool lng   = side_[i];
                const bool stop  = lng ? (ltp <= stop_[i])   : (ltp >= stop_[i]);
                const bool tgt   = lng ? (ltp >= target_[i]) : (ltp <= target_[i]);
                const bool time  = (now >= deadline_ns_[i]);
                hit |= std::uint64_t(match & (stop | tgt | time)) << i;
            }
            return hit;
        }

    The common case is hit == 0, checked with one test. Only then do you
    branch into the (cold, rare) exit-dispatch path.

    SIMD UPGRADE (only if measurement justifies it — see 12.6): the scan
    vectorises cleanly. With AVX2 on Cascade Lake, 4 int64 comparisons per
    instruction. At 64 positions that is 16 iterations instead of 64. Let the
    compiler auto-vectorise first (-O3 -ftree-vectorize) and check the asm
    before hand-writing intrinsics.

5.9 SPSC RING BUFFER — the inter-thread seam
--------------------------------------------------------------------------------
    template <typename T, std::size_t N>   // N must be a power of two
    class SpscRing {
        static_assert((N & (N - 1)) == 0, "capacity must be a power of two");
        alignas(64) std::atomic<std::size_t> head_{0};   // written by consumer
        alignas(64) std::atomic<std::size_t> tail_{0};   // written by producer
        alignas(64) std::array<T, N> buf_{};
        // Cached copies avoid touching the other thread's cache line.
        alignas(64) std::size_t cached_head_{0};
        alignas(64) std::size_t cached_tail_{0};
      public:
        bool try_push(const T& v) noexcept {
            const auto t = tail_.load(std::memory_order_relaxed);
            if (t - cached_head_ >= N) [[unlikely]] {
                cached_head_ = head_.load(std::memory_order_acquire);
                if (t - cached_head_ >= N) return false;   // full
            }
            buf_[t & (N - 1)] = v;
            tail_.store(t + 1, std::memory_order_release);
            return true;
        }
        bool try_pop(T& out) noexcept { /* mirror image */ }
    };

    THE THREE THINGS PEOPLE GET WRONG:
      1. head_ and tail_ on the SAME cache line -> false sharing, and the
         ring becomes slower than a mutex. alignas(64) on each, separately.
      2. Using memory_order_seq_cst "to be safe" -> emits an mfence you do
         not need. acquire/release is correct and much cheaper.
      3. Not caching the opposite index -> every operation reads the other
         thread's line. The cached_head_/cached_tail_ trick removes most of
         that traffic.

    ON THIS BOX (2 vCPUs), the consumer MUST use a hybrid wait:
        for (int i = 0; i < 1000; ++i) {
            if (try_pop(out)) return true;
            _mm_pause();                 // ~40 cycles, yields the HT sibling
        }
        futex_wait(...);                 // then actually sleep
    A pure spin loop consumes 50% of the machine — see 2.3.

5.10 ALLOCATION STRATEGY
--------------------------------------------------------------------------------
    STARTUP           Allocate everything. Rings, pools, the position book,
                      the symbol tables, the DB statement cache.
                      mlockall(MCL_CURRENT | MCL_FUTURE) so none of it pages.

    HOT PATH          Zero allocation. Enforced, not hoped for:

        // Debug/staging builds only. This is how you actually guarantee it.
        void* operator new(std::size_t n) {
            if (g_market_open.load(std::memory_order_relaxed) &&
                g_hot_thread == std::this_thread::get_id()) [[unlikely]] {
                std::abort();     // fail loudly in test, never in prod
            }
            return std::malloc(n);
        }

    COLD PATH         std::pmr::monotonic_buffer_resource, one arena per
                      announcement, reset (O(1)) when the analysis completes.
                      No per-object frees, no fragmentation.

        std::array<std::byte, 512 * 1024> arena_buf;
        std::pmr::monotonic_buffer_resource arena{arena_buf.data(),
                                                  arena_buf.size()};
        // pass &arena to every pmr container used for this announcement
        arena.release();   // "free" the whole analysis in O(1)

    OBJECT POOLS      Fixed-capacity, intrusive freelist, for Order, Tick
                      batches and Announcement. Acquire/release are two
                      pointer writes.

    WHY THIS MATTERS MOST FOR YOU: your live process is at 1.36 GB RSS on a
    1.9 GB box with 127 MB free. Bounded, pre-allocated memory turns an
    unbounded OOM risk into a fixed, provable footprint. This is the most
    valuable single outcome of the rewrite — more valuable than any latency
    number in this document.

before committing to the project.

Everything below was established by reading the INSTALLED SDK SOURCE at
.venv/Lib/site-packages/fyers_apiv3/, not from documentation. Fyers' public

7.1 WHAT YOU ACTUALLY DEPEND ON
--------------------------------------------------------------------------------
fyers-apiv3 is a Python SDK. There is no official C++ SDK and no credible
third-party one. Your system uses four distinct surfaces, and they are NOT
equally hard to port. Treat them as four separate projects.

  Surface        Transport / URL                          Protocol      Port
  ---------------------------------------------------------------------------
  OAuth          https://api-t1.fyers.in/api/v3           HTTPS + JSON  EASY
  REST           https://api-t1.fyers.in/api/v3           HTTPS + JSON  EASY
                 https://api-t1.fyers.in/data
  Order socket   wss://socket.fyers.in/trade/v3           JSON frames   EASY
  Data socket    wss://socket.fyers.in/hsm/v1-5/prod      CUSTOM BINARY HARD

  (A fourth socket, tbt_ws -> wss://rtsocket-api.fyers.in/versova, uses
  protobuf. You do NOT currently use it. See 7.6 — it may be your escape
  hatch.)

  CORRECTION TO A NATURAL ASSUMPTION: the package ships msg_pb2.py, which
  makes it look like the data feed is protobuf. It is not. msg_pb2 is
  imported ONLY by tbt_ws.py. The data socket you actually use (data_ws.py,
  68 KB) decodes a hand-rolled binary format with struct.unpack. Verify this
  yourself before planning around it:

      grep -l msg_pb2 .venv/Lib/site-packages/fyers_apiv3/FyersWebsocket/*.py

7.2 OAUTH + REST — the easy 60%
--------------------------------------------------------------------------------
WHAT     Token exchange, place/modify/cancel order, funds, positions, quotes,
         history. All request/response JSON over HTTPS.

C++      libcurl multi handle + simdjson parse + glaze serialise.
         Auth header format: Authorization: <app_id>:<access_token>
         (already documented in app/execution/fyers_live.py:41).

PORT     app/execution/fyers_auth.py     269 lines  -> ~400 C++
         app/execution/fyers_live.py   1,242 lines  -> ~2,000 C++
         app/api/fyers_callback.py       523 lines  -> ~700 C++

RISK     LOW. Fully testable against a mock server, and every response shape
         is already captured in your suite (test_fyers_live.py: 24 tests,
         test_fyers_auth.py: 23 tests). Port those tests FIRST, then the code.

GOTCHAS THAT MUST SURVIVE THE PORT (all learned painfully in production):

  - IPv4 ONLY. The instance is dual-stack; Fyers whitelists only the IPv4
    static IP. Over IPv6 every live order is rejected with -50. /etc/gai.conf
    already forces v4 precedence — in C++, ALSO set
    CURLOPT_IPRESOLVE = CURL_IPRESOLVE_V4 explicitly. Do not rely on gai.conf
    alone. Note curl is a bad verifier here (happy-eyeballs prefers v6);
    verify with the actual client library.

  - The access token expires DAILY and is re-authed by hand through the UI.
    The C++ client must reload it on broker.token_rotated without a restart,
    exactly as the Python manager does today.

  - app_id must match the dashboard the app was created in. A wrong-app order
    is rejected in a way that looks like an auth failure. The fix sequence is
    activate -> disconnect -> reconnect.

  - Rate limit is ~10 req/s. The REST quote path used to hammer this and
    caused constant 429s — that is WHY the data socket exists. Keep REST as a
    backstop only, never as the primary price source.

--------------------------------------------------------------------------------
7.4 DATA SOCKET — the actual hard problem
--------------------------------------------------------------------------------
URL      wss://socket.fyers.in/hsm/v1-5/prod
FORMAT   Undocumented custom binary. Big-endian, length-prefixed, with field
         ordering supplied by a shipped map.json.

FRAME LAYOUT (reconstructed from data_ws.py — verify against real captures
before trusting it):

    offset  size  meaning
    ------------------------------------------------------------------
    0..2     3    header / message class
    3..6     4    message_num                  (>I  big-endian uint32)
    7..8     2    scrip_count                  (!H  big-endian uint16)
    9..      -    scrip_count repetitions of:
                    1    data_type             (B)
                           83 ('S') = snapshot
                           other    = incremental update
                    2    topic_id              (H)
                    1    topic_name_len        (B)
                    N    topic_name            (utf-8)
                           prefix "dp" => depth topic
                           otherwise   => quote topic
                    1    field_count           (B)
                    4*F  field values          (>i  signed int32)
                           sentinel -2147483648 == "field absent"
                    2    trailing / padding

FIELD ORDER is positional and comes from map.json -> "data_val":

    ltp, vol_traded_today, last_traded_time, exch_feed_time, bid_size,
    ask_size, bid_price, ask_price, last_traded_qty, tot_buy_qty,
    tot_sell_qty, avg_trade_price, OI, low_price, high_price, Yhigh, Ylow,
    lower_ckt, upper_ckt, open_price, prev_close_price, type, ...

    (depth topics use a separate ordering — see map.json)

STATEFULNESS — the part that makes this genuinely hard:

  - topic_id -> topic_name is learned from SNAPSHOT frames and reused by all
    later incremental frames. The decoder MUST hold that mapping. Miss one
    snapshot and every subsequent update for that symbol is unattributable.

  - Incremental frames carry ONLY CHANGED fields. The decoder maintains a
    per-topic running state; the current price is a snapshot plus every delta
    since. A single dropped or misparsed frame silently corrupts price state
    until the next snapshot arrives.

  - ACKNOWLEDGEMENTS: after ack_count updates the client must send an ack
    message carrying message_num. Fail to ack and the server throttles or
    disconnects you.

  - Prices arrive as SCALED INTEGERS, not floats. The scale factor differs by
    field and segment. Get it wrong and you are off by 100x, on the money
    path, with no exception raised.

WHY THIS IS DANGEROUS

  A bug here does not crash. It produces PLAUSIBLE WRONG PRICES, which flow
  into MarketDataBus, which drives stop-loss and target evaluation. The
  failure mode is a silently mistimed exit — real losses, with green health
  checks. Invariant I2 (never fill at an invented price) does NOT protect you
  here, because the price is not obviously invalid. It is just wrong.

  This is the single strongest argument for the sidecar in 7.5.

7.5 THE RECOMMENDED PATH — three stages
--------------------------------------------------------------------------------

STAGE 1 (Phases 1-11): PYTHON FYERS SIDECAR, DATA SOCKET ONLY

    Keep a minimal Python process whose ONLY job is the data socket. It
    speaks fyers-apiv3 on one side and a Unix domain socket to the C++ binary
    on the other.

        fyers_sidecar.py  --unix socket-->  C++ tradebot
          data_ws ticks   ->  fixed-layout POD structs

    Protocol: length-prefixed POD structs, NOT JSON. You control both ends,
    so pay nothing for serialisation.

        struct WireTick {            // 48 bytes, stable layout, no padding
            uint32_t symbol_id;      // resolved by the sidecar
            uint32_t seq;
            int64_t  ltp_e2;         // paise as integer — no float on the wire
            int64_t  bid_e2;
            int64_t  ask_e2;
            int64_t  volume;
            uint64_t exch_feed_time_ns;
            uint32_t flags;
        };
        static_assert(sizeof(WireTick) == 48);

    Cost: roughly 200 us of IPC per tick. Against a 34.3 s exchange lag that
    is invisible, and it lets you migrate 100% of the rest of the system
    while the riskiest component keeps running code that already works.

    THIS IS NOT A COMPROMISE. It is the correct engineering call: it isolates
    the one component you cannot safely rewrite until everything else is
    proven, and it keeps a working trading system at every point.

STAGE 2 (Phase 11, same phase): PORT OAUTH + REST + ORDER SOCKET

    Per 7.2 and 7.3, all three are JSON and low risk. After this stage the
    sidecar handles ONLY the data socket — roughly 150 lines of Python.

STAGE 3 (Phase 13): PORT THE DATA SOCKET

    Only after everything else has been in production and stable for 30+
    trading days. Then, in order:

      a) Capture a full trading day of RAW WebSocket frames. Do this back in
         Phase 0 — you need the corpus long before you need the decoder, and
         you cannot capture the past.
      b) Write the C++ HSM decoder against the recorded frames OFFLINE. No
         network, fully deterministic, fuzzable, re-runnable in CI.
      c) Byte-compare: run the C++ decoder and the Python SDK over the SAME
         recorded frames; assert identical decoded output for every tick and
         every field.
      d) SHADOW live for 20+ trading days: C++ decoder and sidecar both
         connected, every tick compared in real time, mismatches logged and
         alerted.
      e) Retire the sidecar ONLY on zero mismatches across the whole window.

    STOP RULE: if the byte comparison ever disagrees and you cannot explain
    why, KEEP THE SIDECAR. A permanent 150-line Python process is a perfectly
    good engineering outcome. A subtly wrong tick decoder is not.

7.6 THE tbt_ws ESCAPE HATCH — evaluate this EARLY
--------------------------------------------------------------------------------
fyers-apiv3 ships a THIRD socket, tbt_ws.py, at
wss://rtsocket-api.fyers.in/versova, and it uses PROTOBUF (msg_pb2.py) with a
schema that is fully recoverable from the shipped descriptor:

    SocketMessage { type; map<string,MarketFeed> feeds; bool snapshot;
                    string msg; bool error }

    MarketFeed    { Quote quote; ExtendedQuote eq; DailyQuote dq;
                    OHLCV ohlcv; Depth depth;
                    uint64 feed_time; uint64 send_time; string token;
                    uint32 sequence_no; bool snapshot; string ticker;
                    SymDetail symdetail }

    Quote         { ltp; ltt; ltq; vtt; vtt_diff; oi; ltpc }
    ExtendedQuote { atp; cp; lc; uc; yh; yl; poi; oich; pc }
    DailyQuote    { do; dh; dl; dc; dhoi; dloi }
    OHLCV         { open; high; low; close; volume; epoch }
    Depth         { tbq; tsq; repeated MarketLevel asks; bids }
    MarketLevel   { price; qty; nord; num }

Recover the schema and generate C++ bindings:

    python -c "from fyers_apiv3.FyersWebsocket import msg_pb2; \
      from google.protobuf import descriptor_pb2 as d; \
      p = d.FileDescriptorProto(); msg_pb2.DESCRIPTOR.CopyToProto(p); \
      open('msg_descriptor.bin','wb').write(p.SerializeToString())"

    # reconstruct msg.proto from the descriptor, then:
    protoc --cpp_out=. msg.proto

WHY THIS MATTERS ENORMOUSLY: if tbt_ws carries the price data your strategy
needs, porting it to C++ is dramatically easier and safer than the HSM binary
decoder. Protobuf is self-describing, versioned, and GENERATED rather than
hand-written — no stateful delta accumulation, no positional field ordering,
no scale-factor guessing, no ack bookkeeping. It removes the single largest
technical risk in this entire plan.

ACTION BEFORE PHASE 13 — do this in week one, it costs one day:

    1. Confirm your Fyers account is entitled to the tbt / versova feed.
       (It may be a paid or derivatives-only add-on.)
    2. Confirm it carries LTP / bid / ask for NSE CASH EQUITIES, not just
       depth or tick-by-tick for derivatives.
    3. Compare its latency against the HSM feed over one full trading day.

    If all three pass, Stage 3 becomes "generate protobuf bindings" instead
    of "reverse-engineer a stateful binary protocol." One day of checking can
    save three months of work and the largest risk in the project.

7.7 SIDECAR DESIGN DETAIL
--------------------------------------------------------------------------------
PROCESS    Separate systemd unit, tradebot-fyers-sidecar.service.
           Restart=always, RestartSec=2, after tradebot-cpp.service.

TRANSPORT  Unix domain socket, SOCK_SEQPACKET — preserves message boundaries
           so you write no framing code at all.
           /run/tradebot/fyers.sock, mode 0600, owned by the service user.

FLOW       sidecar -> C++ : WireTick, WireOrderUpdate, WireStatus
           C++ -> sidecar : Subscribe{symbol_ids}, Unsubscribe, Ping

SYMBOLS    The sidecar resolves "NSE:THOMASCOOK-EQ" -> symbol_id using the
           SAME perfect-hash table the C++ side uses, generated from the
           instrument master at build time and emitted as both a C++ header
           and a Python module. Symbols never cross the wire as strings on
           the hot path.

BACKPRESSURE  Ring buffer on the C++ side. If it fills, DROP with a counter
           and alert — never block the reader thread. A blocked reader means
           a stalled exit check.

FAIL-SAFE RULES (the most important part of this section):

  - Heartbeat every 1 s. If C++ misses 3 consecutive heartbeats: HALT
    TRADING, alert Telegram, keep the REST reconcile sweep running.

  - Sidecar death => C++ treats prices as stale => NO_LIVE_PRICE => entries
    blocked (invariant I2). It must NEVER fall back to a last-known price for
    an entry decision.

  - For EXITS, stale prices are MORE dangerous than no prices. If the feed
    dies while a position is open, escalate to REST polling immediately and
    alert loudly. Never silently hold a position on a dead feed.

  - The silence watchdog that already exists in Python (_recover_if_silent,
    60 s, commit f158226) MUST be reimplemented on the C++ side. This exact
    bug cost a full trading day once already: the socket connected
    pre-market, took a handful of frames, then never ticked after the open,
    while REST quotes kept working so the dashboard looked healthy.
    Diagnostic signal: received frozen while is_market_open() is true.
    Do not rediscover this the hard way in C++.

================================================================================
SECTION 8 — HFT TECHNIQUE CATALOGUE
================================================================================
Each technique, what it is, where it applies in THIS system, and an honest
verdict. "LOAD-BEARING" means it measurably improves a path that matters here.
"SHOWCASE" means it is correct HFT practice but your bottleneck is elsewhere —
implement it for craft and defensibility, not for a latency claim.

--------------------------------------------------------------------------------
8.1 ZERO HEAP ALLOCATION IN THE HOT PATH
--------------------------------------------------------------------------------
WHAT      Never call new/malloc/std::vector growth during market hours.
          Pre-allocate everything at startup.

WHERE     - Tick decode buffers (Fyers data WS)
          - Order{} objects on the exit path
          - MarketDataBus quote slots
          - The per-announcement arena in the cold path

HOW       - std::pmr::monotonic_buffer_resource for per-event arenas, reset
            after each event (O(1) "free")
          - Fixed-capacity object pools with an intrusive freelist for
            Tick, Order, Quote, Position
          - Reserve every container at startup; assert capacity in debug
          - boost::container::static_vector / small_vector for bounded lists
          - Replace std::string with fixed char[N] + std::string_view on the
            hot path (symbols are <= 32 chars — make it a struct Symbol{char[32]})
          - Custom global operator new that ABORTS if called during market
            hours in debug builds. This is how you actually enforce it.

VERDICT   LOAD-BEARING for the tick/exit path. Also directly attacks your
          real problem: 1.36 GB RSS → predictable, bounded memory. This is the
          single most valuable technique in the list FOR YOUR SYSTEM, because
          it fixes a live OOM risk, not a hypothetical latency one.

--------------------------------------------------------------------------------
8.2 CACHE-LINE ALIGNMENT AND FALSE-SHARING AVOIDANCE
--------------------------------------------------------------------------------
WHAT      Lay out data so a CPU fetch pulls everything needed in one 64-byte
          cache line, and so two threads never write to the same line.

WHERE     - SPSC ring buffer head/tail indices (classic false-sharing bug)
          - Tick / Order / Position structs
          - The managed-position table scanned on every tick

HOW       - alignas(64) on ring head and tail, separately
          - std::hardware_destructive_interference_size (C++17)
          - Pack Tick to <= 64 bytes: symbol_id(4) ltp(8) bid(8) ask(8)
            volume(8) ts_ns(8) flags(4) = 48 bytes, fits with room
          - Use symbol_id (uint32 index) not symbol strings in hot structs
          - Struct-of-Arrays for the position scan: separate arrays of
            stop_loss[], target[], symbol_id[] so the stop check streams
            linearly instead of chasing pointers
          - static_assert(sizeof(Tick) <= 64) so it cannot regress

VERDICT   LOAD-BEARING for the tick path. The SoA position scan is the
          highest-value layout change: it turns "check every open position on
          every tick" into a linear scan the prefetcher handles perfectly.

--------------------------------------------------------------------------------
8.3 LOCK-FREE SPSC RING BUFFERS
--------------------------------------------------------------------------------
WHAT      Threads hand off data through atomics instead of mutexes.

WHERE     - feed thread → strategy (same thread here, but keep the seam)
          - hot thread → worker pool (order dispatch, DB writes, logging)
          - sidecar socket reader → hot thread

HOW       - Power-of-two capacity, mask instead of modulo
          - alignas(64) std::atomic<size_t> head, tail (separate lines)
          - memory_order_acquire on read, memory_order_release on write.
            NEVER seq_cst — it emits an mfence you do not need.
          - Cache the opposite index locally to avoid touching the other
            thread's cache line on every operation
          - Bounded: on full, drop-with-counter for telemetry, block for
            orders. Decide per ring and document it.

CRITICAL  See 2.3. With 2 vCPUs, do NOT spin forever. Use:
              for (int i = 0; i < 1000; ++i) { if (try_pop()) return; _mm_pause(); }
              futex_wait(...);
          A pure spin loop on this box starves the rest of the system.

VERDICT   LOAD-BEARING for correctness and determinism. The current asyncio
          bus puts monitors, the LLM client and tick handling on ONE event
          loop — a slow PDF parse can delay a stop-loss check today. Splitting
          them is a genuine architectural improvement, independent of speed.

--------------------------------------------------------------------------------
8.4 DEVIRTUALISATION — CRTP, std::variant, if constexpr
--------------------------------------------------------------------------------
WHAT      Remove vtable indirection so the compiler can inline across the
          call.

WHERE     - TradingBackend (paper vs live)
          - Notifier (telegram / email / discord / webhook)
          - VolatilityProvider, VolatilityRegime
          - Monitor base class (NSE / BSE / RSS)

HONEST NOTE (important — do not blindly apply CRTP here):
          CRTP works when the type is known at COMPILE time. Your
          paper-vs-live backend is chosen at RUNTIME by an operator toggle
          (invariant I4/I7). CRTP is the wrong tool for it.

HOW       - Hot path (backend dispatch on order send):
                std::variant<PaperBackend, FyersBackend> + std::visit
            → no vtable, compiler sees both bodies, inlines, and the branch
              predictor nails it because the mode rarely changes.
          - Cold path (notifiers, monitors): keep virtual. It runs once per
            filing at most; a vtable lookup is ~2 ns against a 34 s lag.
            Using CRTP here would add template complexity for zero gain —
            that is exactly the over-engineering this project avoids.
          - Static polymorphism via templates for the rules-engine predicate
            evaluation, where the operator's rule set is compiled once per
            change.

VERDICT   LOAD-BEARING on the order path (variant), SHOWCASE elsewhere.
          Deliberately NOT applying CRTP to the cold path is a defensible
          engineering decision — write it down.

--------------------------------------------------------------------------------
8.5 FORCED INLINING, constexpr, AND COMPILE-TIME WORK
--------------------------------------------------------------------------------
WHAT      Move work from runtime to compile time; eliminate call overhead.

WHERE     - parse_inr_crore, price math, R-multiple, slippage %
          - market_clock: session boundaries, square-off time
          - event_profiles lookup tables
          - Symbol → id mapping (perfect hash, built at compile time)

HOW       - [[gnu::always_inline]] on the tick-path leaves
          - constexpr/consteval for all lookup tables and thresholds
          - A compile-time perfect hash (gperf or frozen::unordered_map) for
            the ~2,000 NSE symbols → symbol_id. Zero-allocation, O(1), no
            hashing collisions at runtime.
          - constexpr parsing of the rules DSL where the rule set is static
          - `frozen::` containers for all read-only maps

VERDICT   LOAD-BEARING (perfect hash + SoA is a genuine tick-path win).
          Everything else SHOWCASE but cheap.

--------------------------------------------------------------------------------
8.6 BRANCH PREDICTION AND BRANCHLESS CODE
--------------------------------------------------------------------------------
WHAT      Help or eliminate the branch predictor.

WHERE     - Stop-loss / target comparison on every tick
          - The "is this a trading day / in-session" check
          - Error paths (always [[unlikely]])

HOW       - [[likely]] / [[unlikely]] attributes (C++20)
          - Branchless min/max and conditional-move formulations for the
            stop check:
                triggered |= (ltp <= stop) & is_long;
            instead of nested ifs
          - Hoist all invariant checks out of the per-position loop
          - Sort positions so the common case streams first

VERDICT   LOAD-BEARING for the per-tick position scan. Measure with
          `perf stat -e branch-misses` before and after — do not assume.

--------------------------------------------------------------------------------
8.7 CACHE WARMING
--------------------------------------------------------------------------------
WHAT      Periodically run fake data through the hot path so its code and
          data stay in L1/L2 during quiet periods.

WHERE     - The exit-evaluation path (your market has minutes of silence
            between filings, and the first real tick after silence is the one
            that matters)
          - The order-dispatch path

HOW       - A warming timer on the hot thread, every ~100 ms during market
            hours, running a synthetic Tick through the full evaluation
            against a sentinel position that can never trigger
          - Guard it so warming can NEVER emit an order: separate the pure
            evaluation function from the side-effecting dispatch, and warm
            only the pure half. Enforce with a type: warm() takes an
            EvaluateOnly tag.
          - Also warms the TLB and keeps the branch predictor trained

VERDICT   SHOWCASE-to-marginal. Real HFT value, but a cold L1 costs ~10 us
          and your entry decision is already 34 s old. Worth implementing for
          the exit path (where you may hold a position for minutes and the
          triggering tick arrives after silence) and worth benchmarking
          honestly — report the real delta, whatever it is.

--------------------------------------------------------------------------------
8.8 KERNEL BYPASS
--------------------------------------------------------------------------------
WHAT      Map the NIC directly into user space, skipping the kernel network
          stack entirely (Solarflare OpenOnload, DPDK, ef_vi).

WHERE     Would apply to: Fyers data WS ingest.

STATUS ON YOUR BOX: **NOT POSSIBLE.**
          - NIC is `ena` (AWS paravirtualised adapter), not Solarflare or
            Mellanox
          - You are a KVM guest, not bare metal
          - Lightsail gives no control over NIC or SR-IOV passthrough

WHAT YOU CAN DO INSTEAD (all achievable on this box):
          - io_uring for socket I/O (kernel 7.0 — full feature set)
            → registered buffers, registered files, SQPOLL off (costs a vCPU)
          - TCP_NODELAY on every socket (disable Nagle)
          - TCP_QUICKACK
          - SO_RCVBUF / SO_SNDBUF sized explicitly
          - recvmmsg / sendmmsg batching
          - SO_BUSY_POLL — possible but burns a vCPU; benchmark, probably no
          - MSG_ZEROCOPY on send for large payloads

VERDICT   NOT AVAILABLE. Document it honestly rather than claiming it. If you
          want true kernel bypass, see Appendix D — it is an infrastructure
          decision, not a code decision, and it would cost more than the
          rewrite.

--------------------------------------------------------------------------------
8.9 PGO AND BOLT
--------------------------------------------------------------------------------
WHAT      Profile-guided optimisation: compile, run a representative
          workload, recompile using the observed branch/call profile. BOLT
          then re-lays-out the binary's code by hot/cold basic blocks.

WHERE     Whole binary.

HOW       - Phase A: -fprofile-generate, run the parity harness replay
            (Section 10) over a full day of recorded real filings + ticks
          - Phase B: -fprofile-use -fprofile-correction
          - Phase C: llvm-bolt with perf-collected profile, -reorder-blocks
            =ext-tsp -reorder-functions=hfsort+ -split-functions
          - Automate in CMake so it cannot rot

VERDICT   LOAD-BEARING and badly underrated. Typically 5–15% on branchy,
          I-cache-bound code like a rules engine — with zero source changes
          and zero hardware requirement. Do this before hand-optimising
          anything. Your replay corpus (20,841 real analyses) makes it easy.

--------------------------------------------------------------------------------
8.10 HUGE PAGES
--------------------------------------------------------------------------------
WHAT      2 MB pages instead of 4 KB to reduce TLB misses.

WHERE     The pre-allocated arena and object pools.

HOW       - Explicit hugetlbfs, NOT transparent huge pages (THP causes
            latency spikes from khugepaged — disable THP: `never`)
          - Reserve at boot: vm.nr_hugepages
          - mmap(MAP_HUGETLB) for the arena
          - Budget carefully: you have 1.9 GB total

VERDICT   MARGINAL here. Your working set after the rewrite should be <150 MB,
          which fits in a handful of huge pages. Do it for the arena;
          benchmark the TLB miss rate (`perf stat -e dTLB-load-misses`) to
          prove it helped rather than assuming.

--------------------------------------------------------------------------------
8.11 CPU PINNING, isolcpus, nohz_full, SCHED_FIFO
--------------------------------------------------------------------------------
STATUS ON YOUR BOX: pinning/isolcpus/nohz_full **NOT VIABLE** (2 vCPUs).

WHAT YOU CAN DO:
          - SCHED_FIFO priority 50 on the hot thread, with
            /proc/sys/kernel/sched_rt_runtime_us capped so a runaway hot
            thread cannot lock you out of the box (set to 600000/1000000)
          - `chrt` verification in the deploy script
          - Set the process to a low `nice` for worker threads
          - Pin the hot thread to vCPU 0 and workers to vCPU 1 as a soft
            affinity — helps cache locality even without isolation

VERDICT   PARTIAL. SCHED_FIFO is the real win; isolation needs Appendix D.

--------------------------------------------------------------------------------
8.12 TIMESTAMPING AND MEASUREMENT
--------------------------------------------------------------------------------
WHAT      You cannot optimise what you cannot measure, and averages lie.

HOW       - rdtscp (with a calibrated TSC→ns conversion) for intra-process
            timing; CLOCK_MONOTONIC_RAW for anything crossing a boundary
          - Check constant_tsc + nonstop_tsc in /proc/cpuinfo flags before
            trusting rdtsc under KVM. If unreliable, fall back to
            clock_gettime (vDSO, ~20 ns).
          - HdrHistogram for every hot-path stage. Record p50/p99/p99.9/max.
            NEVER report a mean.
          - A lock-free telemetry ring: hot thread writes timestamps, a
            worker drains and aggregates. Measurement must never block.

VERDICT   LOAD-BEARING — this is the technique that makes all the others
          honest. Build it in Phase 2, before any optimisation.

--------------------------------------------------------------------------------
8.13 EXCEPTION AND RTTI POLICY
--------------------------------------------------------------------------------
WHAT      Exceptions cost nothing when not thrown, but the throw path is
          slow and non-deterministic.

HOW       - Hot path: no exceptions. Return std::expected<T,E> (C++23).
            Compile the hot-path static library with -fno-exceptions
            -fno-rtti where dependencies allow.
          - Cold path: exceptions fine, they simplify error handling and the
            path is network-bound anyway.
          - NEVER let an exception cross the hot-thread boundary — wrap the
            thread entry in a catch-all that logs and halts trading (fail
            safe, per I2: block, never guess).

VERDICT   LOAD-BEARING on the order path.

SECTION 10 — THE PARITY HARNESS
================================================================================
This is the most important artifact in the migration. Build it in Phase 0 and
extend it every phase. Without it, you are rewriting 52,000 lines of
money-handling logic on hope.

10.1 PRINCIPLE

    For any recorded input, the C++ system must produce the same decision as
    the Python system, or the difference must be explained and approved in
    writing. "Approved" means a line in a DIFFS.md file with a reason.

10.2 MECHANISM

    corpus/<announcement_id>/
        raw_feed.json        bytes as scraped
        filing.pdf           bytes as fetched
        extracted.txt        Python's extraction
        prompt.txt           rendered prompt
        llm_response.json    DeepSeek's reply (recorded, replayed — never
                             re-called; the LLM is non-deterministic)
        expected.json        Python's rules + risk decision, sizing, levels,
                             block reasons

    replay_cpp <corpus_dir>   → actual.json
    diff expected.json actual.json

10.3 WHAT MUST MATCH EXACTLY

    - event_type, recommendation, confidence, sentiment_score
    - rule matched (id and name)
    - risk approved/blocked + block reason string
    - position size (quantity), entry, stop_loss, target
    - every risk_events row that would be written

10.4 WHAT MAY LEGITIMATELY DIFFER (record each in DIFFS.md)

    - Floating-point last-digit differences. Define a tolerance (1e-9
      relative) and enforce it; do NOT let it hide a real logic change.
    - Timestamps.
    - Log field ordering.

10.5 TICK REPLAY

    Separately, replay the recorded Fyers WS day through the exit path and
    assert identical exit triggers, at identical tick indices. This is how
    Phase 9 earns trust.

10.6 CONTINUOUS

    Run the full parity suite in CI on every commit. A phase is not done when
    the code compiles; it is done when parity is green.

11.7 PGO WORKFLOW (Phase 12 — do this BEFORE hand-optimising anything)

    # 1. Instrumented build
    cmake --preset pgo-gen && cmake --build --preset pgo-gen

    # 2. Run a REPRESENTATIVE workload. You have the perfect corpus:
    #    20,841 real analyses + one full day of recorded ticks.
    ./build/pgo-gen/tradebot --replay corpus/ --ticks captures/2026-08-20.bin

    # 3. Merge and rebuild
    cmake --preset pgo-use && cmake --build --preset pgo-use

    Expect 5-15% on branchy, I-cache-bound code such as the rules engine.
    This is the single best performance-per-effort item in the whole plan:
    zero source changes, zero risk, no hardware requirement.

    CRITICAL: the profile must be representative. Profiling on synthetic data
    that never takes the ORDER_WIN branch will pessimise the branch you care
    about. Use the real corpus.

11.8 BOLT (post-link binary layout)

    perf record -e cycles:u -j any,u -o perf.data -- \
        ./tradebot --replay corpus/
    perf2bolt -p perf.data -o bolt.fdata tradebot
    llvm-bolt tradebot -o tradebot.bolt -data=bolt.fdata \
        -reorder-blocks=ext-tsp -reorder-functions=hfsort+ \
        -split-functions -split-all-cold -icf=1 -use-gnu-stack

    BOLT re-lays-out the binary so hot basic blocks are contiguous. Typical
    additional 5-10% on top of PGO for large branchy binaries. Requires
    -fno-reorder-blocks-and-partition at compile time.

SECTION 12 — PERFORMANCE ENGINEERING MANUAL
================================================================================
This is the section that makes the rewrite defensible. Everything here is
about MEASUREMENT FIRST. The techniques in Section 8 are tools; this section
is the method for deciding which ones to actually use.

--------------------------------------------------------------------------------
12.1 THE RULES
--------------------------------------------------------------------------------
    R1  Measure before optimising. Always. Phase 2 exists solely for this.
    R2  Never report a mean. p50 / p99 / p99.9 / max, or it did not happen.
        An average hides exactly the tail that costs you money.
    R3  Every optimisation carries a committed before/after benchmark.
    R4  Anything that does not measurably help gets REVERTED — including
        techniques from Section 8. Craft is not a justification for keeping
        code that does nothing.
    R5  Optimise the top histogram entry, re-measure, repeat. Never optimise
        down a list by intuition.
    R6  Correctness gates performance: the parity harness (Section 10) must
        be green before AND after every optimisation.
    R7  Benchmark on the TARGET box, not your laptop. A Xeon 8259CL under KVM
        with 2 vCPUs behaves nothing like a desktop.

--------------------------------------------------------------------------------
12.2 TIMING INFRASTRUCTURE
--------------------------------------------------------------------------------
    TSC (rdtscp) is the cheapest clock (~20 cycles) but under KVM you MUST
    verify it is usable first:

        grep -o 'constant_tsc\|nonstop_tsc\|tsc_reliable' /proc/cpuinfo | sort -u

    If constant_tsc and nonstop_tsc are both present, calibrate once at
    startup against CLOCK_MONOTONIC and use rdtscp thereafter. If not, use
    clock_gettime(CLOCK_MONOTONIC) — it is a vDSO call, ~20-25 ns, still
    fine. Do not guess; the plan must record which one you ended up on.

        // Calibrate: spin for 100 ms, compare TSC delta to clock delta.
        inline std::uint64_t rdtscp_now() noexcept {
            unsigned aux;
            return __rdtscp(&aux);
        }

    NEVER use std::chrono::system_clock for measurement — it can step
    backwards on NTP adjustment, which produces negative latencies and
    hours of confusion.

--------------------------------------------------------------------------------
12.3 LATENCY RECORDING — HdrHistogram, not averages
--------------------------------------------------------------------------------
    A mean latency of 40 us with a p99.9 of 8 ms means you exit late once
    every thousand ticks. The mean tells you nothing about that.

        // Per-stage, lock-free: hot thread writes raw samples to a ring,
        // a worker drains and records. Measurement must NEVER block or
        // allocate on the hot path.
        struct LatencySample { std::uint16_t stage; std::uint32_t ns; };
        SpscRing<LatencySample, 65536> g_latency_ring;

        #define TIME_STAGE(stage_id) \
            ScopedTimer _t{stage_id, g_latency_ring}

    STAGES TO INSTRUMENT (each gets its own histogram):
        0  frame recv -> decode complete
        1  decode -> bus publish
        2  bus publish -> position scan complete
        3  scan -> order constructed
        4  order constructed -> pushed to worker ring
        5  worker pop -> HTTPS request sent
        6  END-TO-END: frame recv -> order on the wire

    Expose all of them at /api/metrics/latency as p50/p99/p99.9/max, and put
    stage 6 on the dashboard. If you cannot see it, you will not defend it.

12.4 PROFILING RECIPES (commit these to tools/perf/)
--------------------------------------------------------------------------------
    # Where is time going?
    perf record -F 999 -g --call-graph=fp -- ./tradebot --replay corpus/
    perf report --sort=overhead,symbol

    # Branch misprediction (the position scan and rules engine)

    # Cache behaviour (validates the SoA layout in 5.8)

    perf stat -e cycles,instructions ...     # IPC > 2.0 is healthy

12.5 THE OPTIMISATION CATALOGUE, IN THE ORDER YOU SHOULD APPLY IT
--------------------------------------------------------------------------------
Work top-down. Each step is cheaper and safer than the one below it.

    1. ALGORITHM / DATA LAYOUT          (biggest wins, always first)
       - SoA position book (5.8)
       - Direct-indexed MarketDataBus, no hashing (5.7)
       - SymbolId integers instead of strings (5.5)
       - frozen/perfect-hash tables, zero runtime construction
       Expected: 2-10x on the affected loop.

    2. COMPILER-LEVEL, ZERO SOURCE CHANGE
       - -O3, LTO, -march=cascadelake
       - PGO (11.7)          expect 5-15%
       - BOLT (11.8)         expect a further 5-10%
       Expected: 15-25% cumulative, for a day of work and no risk.

    3. ALLOCATION ELIMINATION
       - Arenas, pools, mlockall (5.10)
       Expected: removes the tail, not the mean. This is where p99.9
       improves dramatically — and the tail is what costs money.

    4. BRANCH AND MEMORY BEHAVIOUR
       - Branchless scan (5.8)
       - [[likely]]/[[unlikely]] on verified-hot branches only
       - __builtin_prefetch ahead of the position scan
       - Software pipelining of the decode loop
       Expected: 10-30% on the specific loop. Verify with branch-misses.

    5. SIMD (only when 1-4 are exhausted — see 12.6)

    6. MICRO-TUNING (inline hints, restrict, reordering)
       Expected: single-digit %. Usually not worth the readability cost.
       Do this last, if at all.

    ANTI-PATTERN WARNING: most engineers start at 6 and never do 1 or 2.
    Step 2 alone will beat every micro-optimisation you could hand-write in
    a month, and it cannot introduce a bug.

--------------------------------------------------------------------------------
12.6 SIMD — WHERE IT ACTUALLY APPLIES HERE
--------------------------------------------------------------------------------
Cascade Lake gives you AVX2 and AVX-512. Genuine opportunities, in order of
value:

    (a) POSITION SCAN (5.8)
        4x int64 compares per AVX2 instruction. 64 positions -> 16 iterations.
        FIRST: try auto-vectorisation. Compile with -O3 and check:
            g++ -O3 -march=cascadelake -fopt-info-vec-missed scan.cpp
        If the compiler already vectorised it, write no intrinsics.

    (b) PDF TEXT SCANNING — your hottest Python function (987 us)
        Do NOT hand-write this. Hyperscan is a SIMD regex engine written by
        people who do this professionally; it will beat anything you write.
        This is the single largest measurable win available in the port.

    (c) JSON PARSING
        simdjson already does it. Use the library; write nothing.

    (d) CHECKSUM / MEMCMP on the parity harness
        std::memcmp is already vectorised by libc.

    RULE: in three of four cases the answer is "use a library that already
    did the SIMD work." Hand-written intrinsics are a last resort, they are
    architecture-specific, and they are where correctness bugs hide.

    IF you do hand-write: always keep a scalar reference implementation and
    assert they agree, on every input, in CI. A SIMD path that disagrees with
    scalar on an edge case is exactly the kind of bug that reaches production.

12.9 WHAT NOT TO CLAIM
--------------------------------------------------------------------------------
    Do NOT claim the rewrite improved signal latency. It cannot: 93% of the
    end-to-end budget is the exchange's publish lag and 6% is DeepSeek's API.
    Claiming otherwise is the fastest way to lose credibility with anyone who
    checks the numbers — and the numbers are in Section 1.

    DO claim, because it is true and provable:
      - deterministic microsecond exit path (previously: Python asyncio on a
        shared event loop with PDF parsing and HTTP clients)
      - ~10x memory reduction, removing a live OOM risk on a 1.9 GB box
      - ~30x faster startup, making mid-session restarts safe
      - zero GC pauses and no GIL contention on the money path
      - bounded, provable resource usage under load

    The honest framing: this rewrite buys DETERMINISM and SAFETY MARGIN on
    the exit path, not faster signals. That is a real engineering result.
    Oversell it and the real result gets dismissed along with the overclaim.

SECTION 17 — ABORT CRITERIA
================================================================================
A plan without a stopping rule is a trap. Stop, and keep Python, if ANY of
these become true. Stopping is not failure — every phase up to that point
shipped something working.

  A1  Phase 5 parity cannot reach zero diffs after 3 weeks of effort. If pure,
      side-effect-free logic will not agree, the money path never will.

  A2  Phase 9 tick→dispatch p99 does not beat 200 us. If the hot path is not
      dramatically faster after applying every technique in Section 8, the
      rewrite has no justification left — the memory win alone is achievable
      in Python for a fraction of the effort.

  A3  Phase 13 tick decoding disagrees with the sidecar and the cause cannot
      be found. Keep the sidecar permanently. (This is a partial stop, not a
      full abort.)

  A4  Six months pass with no phase completed. The project has stalled;
      Python is still running and is still fine.

  A5  A memory-safety bug reaches production and costs real money. Stop, roll
      back to Python, and do not restart without a second pair of eyes on
      every hot-path review.

  HONEST NOTE FOR FUTURE YOU:
  The measured facts at the top of this document have not changed and will
  not: your signal latency is 93% exchange lag and 6% DeepSeek. This rewrite
  buys determinism on the exit path, a 10x memory reduction, and deep C++
  expertise. Those are real and worth having. It does not buy faster signals.
  If at any point the reason for continuing has quietly become "we have come
  this far", that is A4, and Python is still running.

SECTION 18 — HYBRID C++ / PYTHON: HOW THE TWO HALVES CONNECT
================================================================================
Yes, a mixed backend is possible, and this plan depends on it. During the
migration it is the mechanism; afterwards it is the permanent architecture
for the parts that should never be C++ (6.1, 7.5).

This section specifies the four connection mechanisms, when to use each, and
their measured cost. Choose by latency requirement, not by taste.

--------------------------------------------------------------------------------
18.1 THE FOUR MECHANISMS
--------------------------------------------------------------------------------
  Mechanism           Latency     Use for                        Complexity
  -----------------------------------------------------------------------------
  1 Shared database   ms          Anything not time-critical     None
  2 Unix socket       ~50-200 us  Fyers sidecar ticks, RPC       Low
  3 Shared memory     ~0.5-2 us   Tick fan-out at high rate      Medium
  4 Embedding         ~1-10 us    Calling ML models inline       High (avoid)

  DEFAULT TO 1. Escalate only when a measurement says you must. Most of the
  boundaries in this system are crossed once per filing — roughly 2,700 times
  a day — where even 10 ms would be invisible.

--------------------------------------------------------------------------------
18.2 MECHANISM 1 — SHARED SQLITE (the primary seam)
--------------------------------------------------------------------------------
WHAT     Both processes open the same data/trading.db in WAL mode.

USE FOR  - The entire strangler-fig migration (Section 4)
         - dataset_builder.py writing dataset_features while C++ trades
         - AIdataset/ reading everything, forever
         - Any read-only Python tooling

RULES (violate these and you will get SQLITE_BUSY storms at the worst time):
  - WAL mode, always:            PRAGMA journal_mode=WAL;
  - busy_timeout=30000 in BOTH stacks
  - ONE WRITER PER TABLE. Maintain an ownership table in this document and
    update it as phases complete. Two writers to `trades` is a corruption bug
    waiting for a busy market day.
  - Write transactions use BEGIN IMMEDIATE, never a deferred transaction that
    upgrades mid-flight — that is the classic SQLite deadlock.
  - NEVER hold a write transaction across a network call. The current Python
    code does this in places; fix it during the port rather than reproducing
    it.
  - synchronous=NORMAL is correct under WAL. FULL costs an fsync per commit
    for durability you do not need on a machine with a nightly backup.

TABLE OWNERSHIP DURING MIGRATION (keep this current):
    Table                  Writer after Phase...
    announcements          7   (C++ monitors)
    analyses               8   (C++ analyzer)
    signals, trades        9   (C++ execution)
    positions, risk_*      9   (C++ execution)
    dataset_features       never — stays Python
    audit_log              both (append-only, safe)

--------------------------------------------------------------------------------
18.3 MECHANISM 2 — UNIX DOMAIN SOCKET (the sidecar seam)
--------------------------------------------------------------------------------
WHAT     SOCK_SEQPACKET preserves message boundaries, so you write zero
         framing code. This is why it beats a TCP socket here.

USE FOR  The Fyers data sidecar (7.7), and any Python service the C++ side
         needs to call synchronously.

WIRE FORMAT — fixed-layout POD structs, NOT JSON. You own both ends.

    C++ side:
        struct WireTick {
            std::uint32_t symbol_id;
            std::uint32_t seq;
            std::int64_t  ltp_e2, bid_e2, ask_e2, volume;
            std::uint64_t exch_feed_time_ns;
            std::uint32_t flags;
        } __attribute__((packed));
        static_assert(sizeof(WireTick) == 48);

    Python side (stdlib only, no dependency):
        import struct
        WIRE_TICK = struct.Struct("<IIqqqqQI")   # little-endian, matches
        assert WIRE_TICK.size == 48
        sock.send(WIRE_TICK.pack(sym, seq, ltp, bid, ask, vol, ts, flags))

    THE ONE RULE: a single header file generates both sides, or they WILL
    drift. Emit the Python struct format string from the same codegen step
    that emits the C++ header. A silent layout drift here means silently
    wrong prices.

VERSIONING  First 4 bytes of every message: uint16 msg_type, uint16 version.
            Reject unknown versions loudly at startup rather than
            misinterpreting bytes.

COST        Measured typical: 50-200 us round trip on loopback. Against a
            34.3 s exchange lag this is 0.0006% — irrelevant. Do not optimise
            it without a measurement proving otherwise.

--------------------------------------------------------------------------------
18.4 MECHANISM 3 — SHARED MEMORY RING (only if measurement demands)
--------------------------------------------------------------------------------
WHAT     shm_open + mmap a region containing the same SpscRing<T,N> from
         5.9. Python attaches with the stdlib multiprocessing.shared_memory
         and reads with struct.unpack_from.

USE FOR  High-rate tick fan-out IF the socket ever shows up in the top 3 of
         your latency histogram. It will not, but the design should exist.

CAVEATS  - The ring must be trivially copyable and layout-stable
         - Python's GIL means the Python side still serialises; this helps
           the C++ side, not the Python side
         - Crash recovery is harder: a dead writer leaves indices mid-update.
           Add a generation counter and a heartbeat, and re-init on mismatch.
         - Do not use this before Phase 13. It is an optimisation, and it is
           the wrong thing to be debugging while the system is young.

COST     ~0.5-2 us. That is ~100x better than the socket, buying you 200 us
         on a 36,800,000 us pipeline.

--------------------------------------------------------------------------------
18.5 MECHANISM 4 — EMBEDDING (pybind11 / Python C API) — AVOID
--------------------------------------------------------------------------------
WHY IT LOOKS ATTRACTIVE   Call the sklearn model directly from C++, no IPC.

WHY NOT, HERE:
  - The GIL lands inside your trading process. Any Python call can now stall
    the C++ hot thread. This is precisely the coupling the rewrite exists to
    remove.
  - A Python exception or a segfault in a native extension takes down the
    whole trading process, including open-position management.
  - Deployment gets much worse: the binary now needs a matching Python
    runtime and every C-extension ABI to line up.
  - You lose the process isolation that makes the sidecar fail-safe design
    in 7.7 work at all.

USE INSTEAD  Mechanism 1 for model scores (write predictions to a table) or
             Mechanism 2 for request/response. Both keep the failure domains
             separate, which is worth far more than the microseconds.

THE ONE EXCEPTION  A batch offline tool where a crash costs nothing. Never
             in the trading process.

--------------------------------------------------------------------------------
18.6 THE PERMANENT HYBRID (what this looks like after Phase 14)
--------------------------------------------------------------------------------
    C++ (one binary)                    Python (separate processes)
    -------------------------------     -----------------------------------
    monitors, analyzer, rules           AIdataset/ ML pipeline    [forever]
    risk, execution, exit management     dataset_builder.py        [forever]
    89 REST routes + /ws                 scripts/ seeders          [forever]
    Fyers REST + order socket            fyers_sidecar.py     [until Ph13,
                                                              maybe forever]
              \                                    /
               \--------- SQLite (WAL) -----------/
                          DuckDB warehouse
                          Unix socket (ticks)

    This is not a transitional embarrassment. It is the correct end state:
    C++ where determinism and memory bounds matter, Python where iteration
    speed and library ecosystem matter. Picking one language for the whole
    system would make one half worse.

--------------------------------------------------------------------------------
18.7 OPERATIONAL RULES FOR A SPLIT BACKEND
--------------------------------------------------------------------------------
  - ONE systemd unit per process, each with Restart=always and its own
    health endpoint or heartbeat.
  - The C++ process is the trading authority. If any Python component dies,
    C++ must degrade safely (block entries, alert) — never trade blind.
    Invariant I2 applies across the process boundary.
  - Structured logs from both must share a correlation id so one filing can
    be traced end to end across processes. Emit the same JSON shape from
    spdlog and structlog.
  - Deploy them together, version them together. A version-skew matrix
    between two processes on the money path is not a problem you want.
    Refuse to start if versions disagree.
  - Keep ONE deploy script that handles both, extending deploy/update.sh, so
    they cannot drift out of sync by accident.

APPENDIX B — LIBRARY DECISION RECORDS
================================================================================

  B1  Drogon over Crow/Pistache/oat++
      Reason: async by default, native WebSocket (you need /ws for the
      dashboard), HTTP/2, coroutine support, actively maintained, ORM-ish
      DB layer you can ignore. Crow is simpler but sync-first.

  B2  glaze over nlohmann/json for DTOs
      Reason: compile-time reflection gives you pydantic-like struct
      binding with zero runtime cost. nlohmann is ergonomic but allocates
      heavily — unacceptable in the hot path.

  B3  simdjson for parsing, glaze for writing
      Reason: simdjson is the fastest parser available (on-demand API, no
      DOM allocation). Use it for LLM responses and exchange JSON.

  B4  Hyperscan over RE2 for PDF body scanning
      Reason: your hottest function scans one 11.6 KB body for many order-
      context patterns. Hyperscan is purpose-built for simultaneous
      multi-pattern matching. RE2 for everything else (single patterns,
      simpler API). std::regex is banned outright — it is slower than
      Python's re.

  B5  MuPDF C API over Poppler
      Reason: it is the exact library PyMuPDF wraps. Identical extraction
      behaviour is a migration requirement, not a preference.

  B6  SQLiteCpp + hand-written SQL over any C++ ORM
      Reason: no C++ ORM is mature enough to be worth the abstraction, and
      you only have 18 tables. Hand SQL with a prepared-statement cache is
      faster, clearer, and debuggable.

  B7  spdlog with a JSON pattern over a custom logger
      Reason: async, fast, and matching structlog's output shape means your
      existing journalctl/grep workflows survive the migration untouched.

  B8  rigtorp::SPSCQueue as reference over hand-rolled
      Reason: lock-free queues are notoriously subtle. Read a proven one,
      understand every line, then decide whether you truly need your own.

  B9  libcurl multi over cpp-httplib/Beast
      Reason: HTTP/2 multiplexing, battle-tested TLS, connection reuse —
      matching the persistent-client behaviour that was already measured as
      a real latency win in the Python system.

  B10 doctest over Catch2/GTest
      Reason: dramatically faster compile times, which matters when you are
      porting 825 tests.

================================================================================
If you want the techniques marked NOT POSSIBLE in Section 2, the blocker is
hardware, not code. Decide this BEFORE Phase 9, because it changes the

  D1  MINIMUM FOR REAL KERNEL BYPASS
      - Bare metal (not KVM): AWS *.metal, or a colo/dedicated server
      - Solarflare X2522 or Mellanox ConnectX-5/6 NIC
      - >= 8 physical cores so you can isolate 2-3
      - OpenOnload or ef_vi (Solarflare) / VMA (Mellanox) / DPDK
      Cost: roughly 10-40x your current $12/month.

  D2  PHYSICAL PROXIMITY (the only thing that touches your 34.3 s)
      Your dominant latency is the EXCHANGE's publish lag, not the network
      path. Colocation at NSE (Mumbai) does not reduce publish lag — it
      reduces the ~1-2 ms of network transit that you are not currently
      losing anyway. Colocation would NOT help this strategy.
      The only real lever on detection is a faster SOURCE: the RSS racer
      (already built, still OFF) or a paid vendor feed.

  D3  HONEST RECOMMENDATION
      Do not buy hardware for this system. The strategy is comprehension-
      based on a seconds-to-minutes timescale (see the competitive-edge
      analysis). Kernel bypass on a bot that waits 34 seconds for the
      exchange and 2.2 seconds for an LLM is engineering theatre.
      Build the techniques for the craft and the determinism on the exit
      path. Do not build the datacentre.
